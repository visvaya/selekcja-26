# Future scope and known debt

This document tracks confirmed gaps, unverified behavior and optional product ideas. `src/` is the source of truth. The game is playable and the current automated checks pass; the items below are not claims that a corresponding feature is broken.

## Before moving to a personal repository

1. **Start a new Git history from a source-only snapshot.** The existing Site checkout has historical commits made under an author identity different from the required owner identity. A fresh repository avoids importing those historical author records. Do not rewrite the Site's existing Git history. Include `src/`, `index.html`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `tsconfig.json`, `vite.config.ts`, `.gitignore`, `README.md`, `AGENTS.md` and this file. Exclude `.git/`, `node_modules/`, `dist/` and `.openai/` from the portable copy. Initialize the new repository as `main` and set author and committer to the owner identity for its first commit.
2. **Separate hosting configurations.** `.openai/hosting.json` belongs to the current Site and the generated `dist/` is committed there for that deployment workflow. In a new personal repository, build `dist/` from source; the shared `.gitignore` ignores newly generated `dist/`, while the original Site checkout continues tracking files already committed there. Keep the existing Site configuration and deployment unchanged until a new hosting decision is made.
3. **Run the existing checks in the new environment.** Use Node.js 24+, pnpm, `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm typecheck`, `pnpm format:check` and `pnpm build`. Verify the new repository's author and committer metadata and confirm that no secret or generated directory was included. Add a CI workflow for these commands once the hosting platform is chosen.

## Optional product directions requiring a decision

- **Scouting uncertainty:** Reveal only some measurements at the first camp, then expose a more reliable observation afterward. This could make trying less obvious candidates meaningful, but requires balance work and clear disclosure of what a score represents.
- **Tactical random fill:** Offer a separate option that samples complete squads with stronger formation coverage. Keep the current random option genuinely random within group quotas; another algorithm adds complexity and can hide trade-offs from the player.
- **Scenario packs:** Add alternate fictional rosters or dates after the base game is stable. Every pack needs clearly labeled assumptions, validation of positional supply, and save compatibility.
- **Accessibility and presentation:** Evaluate high contrast, reduced motion, pitch text at small widths and a compact comparison view with actual users before redesigning the interface.

## Numbers and sources

- The 26-player tournament limit and a minimum of three goalkeepers follow [UEFA EURO 2026–28 Article 32.01](https://documents.uefa.com/r/Regulations-of-the-UEFA-European-Football-Championship-2026-28/Article-32-Player-lists-Online). Requiring exactly three goalkeepers is a stricter game rule.
- The 23-player test camp, positional quotas, 50-step undo history, event thresholds, ratings, match scores and scoring weights are game assumptions. Candidate details and the 2028 scenario are fictional and require verification before being presented as real scouting data.
- The source-code and test findings above were checked against the repository at the time this file was written. Actual mobile browser behavior and deployment to a VPS were not tested.
